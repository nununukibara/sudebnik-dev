# sudebnik-dev

AIと相談しながら、開発経験が少なくても「何を作るか」から「どう完成を確認するか」まで進めるための公開テンプレートです。

特定のAIサービス、プログラミング言語、製品には依存しません。AIが1体でも複数でも使えます。

## このテンプレートが防ぐこと

- AIが、難しさを理由に最終目標を黙って小さくする
- 承認済みの版目標から、AIが未実装項目を黙って後回しにする
- 試作品を「完成」と呼び、必要な機能が取り残される
- 利用できないAIやツールを前提に計画し、途中で止まる
- チャットが切れたとき、次のAIが状況を復元できない
- 同じ情報を複数の文書へ写し、片方だけ古くなる
- AIごとに作業規則を複製し、古い規則と新しい規則が競合する
- 実装後に都合のよいテストだけを足し、不具合を再現できないまま直ったことにする
- 実装しただけで、検証や人の確認をせず正式版にする
- 秘密情報や実データを誤って公開リポジトリへ入れる

## 読む順（この順で読みます）

**この節が読む順の正本です。**他の文書はここを参照し、順序を書き写しません。

| | 文書 | いつ |
|---|---|---|
| 1 | [HANDOFF.md](./HANDOFF.md) | 初参加時。プロジェクトの前提 |
| 2 | [STATUS.md](./STATUS.md) | 毎回。現在地 |
| 3 | [AGENTS.md](./AGENTS.md) | 初参加時。作業規則 |
| 4 | [docs/SECURITY.md](./docs/SECURITY.md) | 初参加時。**Gitへ入れてはいけないもの。commitの前に必ず** |
| 5 | [docs/PROJECT_BRIEF.md](./docs/PROJECT_BRIEF.md) | 初参加時。目的と最終目標 |
| 6 | [docs/REQUIREMENTS.md](./docs/REQUIREMENTS.md) | 初参加時。合意済みの要件 |
| 7 | [docs/RESOURCES.md](./docs/RESOURCES.md) | 初参加時。使える人・AI・ツール |
| 8 | [docs/AI_COMPATIBILITY.md](./docs/AI_COMPATIBILITY.md) | 初参加時。AIごとの規則読込と能力差 |
| 9 | [docs/TESTING.md](./docs/TESTING.md) | 実装・不具合修正の前。TDDと確認方法 |
| 10 | [WORKLOG.md](./WORKLOG.md) | STATUSから参照された未完了項。中断時点と他AIの作業 |
| 11 | [ROADMAP.md](./ROADMAP.md)・[docs/VERSIONING.md](./docs/VERSIONING.md) | 初参加時と、対象版・版分割を扱うとき |
| 12 | 関係する設計文書と実コード | 作業内容に応じて |

**二度目以降はSTATUSを入口に、RESOURCESの現在の分担と、STATUSが指すWORKLOGの未完了項を確認して始めます。**対象版を扱うときはREQUIREMENTS・ROADMAP・VERSIONINGも照合します。実装・不具合修正の前にはTESTINGを読みます。規則や最終目標が変わったときはAGENTS・PROJECT_BRIEFを、利用するAIや入口が変わったときはAI_COMPATIBILITYを読み直します。

**4のSECURITYだけは別です。**commitする前と公開する前には、毎回その「チェック」の節を見ます。一度読んで終わりにしません。

各文書に何を書くかは[文書の役割](#文書の役割)にあります。

## 最初の使い方

1. このリポジトリをテンプレートとしてコピーする
2. コピー先を、公開・非公開のどちらにするか決める
3. AIへ下の「最初に送る文」を送る
4. AIの質問に答え、[プロジェクト概要](./docs/PROJECT_BRIEF.md)を埋める
5. 利用できる人、AI、CLI、実端末、外部サービスと制約を確認する
6. [AI_COMPATIBILITY.md](./docs/AI_COMPATIBILITY.md)に従い、使うAIが現在のAGENTS.mdを読めているか確認する
7. GitHub上で検査を自動実行するかを決める（[下記](#github上で検査を走らせるか決める)。**費用が発生しうるので既定では動きません**）
8. 最終目標、最初の正式版、途中の版、完成条件を確認してから実装を始める

### 全部を埋めてから始めるのではありません

各文書には記入欄【】が多数あります。**最初に必要なのはごく一部です。**

**着手前に決めるもの**

- [docs/PROJECT_BRIEF.md](./docs/PROJECT_BRIEF.md) の **1〜5**（一文で／利用者と問題／主な利用場面／最終成功条件／最初の正式版）
- [docs/RESOURCES.md](./docs/RESOURCES.md) の判断者と、使うAIを1行

ここまで決まれば、AIがROADMAPとREQUIREMENTSの案を作れます。

**進めながら埋めるもの**

- PROJECT_BRIEFの6以降（入出力の詳細、品質条件、制約など）— 分かった時点で足します
- [docs/ARCHITECTURE.md](./docs/ARCHITECTURE.md) — **設計する前には書けません。**決まっていない項目は「未決定」と書きます
- [docs/TESTING.md](./docs/TESTING.md) — 要件が決まってから
- [HANDOFF.md](./HANDOFF.md) の「開発環境」「ハマりやすい点」— 動かせるようになってから

空欄のまま進めてよい項目は「未定」と書きます。**空欄と「未定」は違います。**空欄はまだ考えていない、「未定」は考えたうえで後回しにすると決めた、という意味です。AIは空欄を見つけたら質問し、「未定」は質問しません。

### AIへ最初に送る文

```text
このリポジトリの README.md にある「読む順」の表に従って、
挙がっている文書を上から全文読んでください。

まだ実装は始めず、未決定の項目を私へ3問以内ずつ質問してください。
回答から、次の5点を分けて提案してください。

1. 私が最終的に実現したい目標
2. 最初に実用できる正式版（v1.0.0）の範囲
3. そこへ至る途中の試作・Alpha・Beta・RC
4. 各版を「できた」と判断する確認方法
5. 利用できる人・AI・ツールと、単独または分担で進める案

難しい部分があっても、私の許可なく最終目標を縮小・削除しないでください。
承認済みの版に入っている項目を、私の許可なく後の版へ移さないでください。
段階分けや後送りを提案する場合は、理由、影響、代案、後の版に残る項目を明示してください。
作業中の別AIがいるか、利用可能なCLIや外部サービスがあるかを私へ確認してください。
私が内容を確認するまで、コード変更や外部公開はしないでください。
```

### AIがファイルを読めない場合

ブラウザのチャットだけを使う場合など、AIがリポジトリを読めないことがあります。その場合は上の文の1〜2行目を次へ置き換え、**内容を貼り付けます。**

```text
これから開発の進め方を決めた文書を貼り付けます。全文を読んでください。
```

貼り付ける順と内容は次のとおりです。

| | 貼るもの | 理由 |
|---|---|---|
| 最初に | [AGENTS.md](./AGENTS.md) | AIが従う規則。これが無いと以降が効きません |
| 次に | [docs/SECURITY.md](./docs/SECURITY.md) | **Gitへ入れてはいけないもの。事故が一番重いので先に渡します** |
| 次に | [docs/PROJECT_BRIEF.md](./docs/PROJECT_BRIEF.md) | 埋めかけで構いません。空欄はAIが質問します |
| 初回のリソース確認 | [docs/RESOURCES.md](./docs/RESOURCES.md) | 利用できる人・AI・ツールと現在の分担 |
| AIや利用経路を変えるとき | [docs/AI_COMPATIBILITY.md](./docs/AI_COMPATIBILITY.md) | 規則の入口と読込確認。ファイルを読めなければ該当節を貼ります |
| 作業を再開するとき | [STATUS.md](./STATUS.md) | 現在地、次の一歩、中断中の作業 |
| STATUSが未完了項を指すとき | [WORKLOG.md](./WORKLOG.md)の該当項 | 中断時点と、別AIが行った作業 |
| 合意済み要件があるとき | [docs/REQUIREMENTS.md](./docs/REQUIREMENTS.md) | 承認済み要件、対象版、受け入れ条件 |
| 版の相談をするとき | [docs/VERSIONING.md](./docs/VERSIONING.md) | 版の分け方と正式版の判定 |
| 実装・不具合修正の前 | [docs/TESTING.md](./docs/TESTING.md) | TDD、確認の種類、完了の条件 |

[HANDOFF.md](./HANDOFF.md)は他の文書への案内が中心なので、貼り付け運用では省いて構いません。

**この使い方には、はっきりした負担があります。**AIがファイルへ書き込めないため、**AIの出力を人がファイルへ写す作業が毎回発生します。**特にSTATUSとWORKLOGは更新の頻度が高いので、負担を強く感じたら、リポジトリを読み書きできるAIへ移ることを検討してください。

会話が長くなってAIが前提を忘れた場合は、AGENTS.mdをもう一度貼り付けます。

## 状態を混同しない

機能は、少なくとも次を分けて表現します。**この6段階はここが正本です。**

1. **提案** — AIまたは人が案を出しただけ。まだ採用されていない
2. **承認済み** — 判断者が作ると決めた
3. **実装済み** — コードまたは文書へ反映した。まだ確認前かもしれない
4. **検証済み** — 合意した確認を通した
5. **採用済み** — 判断者が結果を確認して採用した
6. **リリース済み** — 版として公開・配布した

「実装済み」と「完成」は同じではありません。

なお、これは**個々の機能の状態**です。版そのものの進み具合には[ROADMAP.md](./ROADMAP.md)の別の語（`提案`／`承認済み`／`開発中`／`検証中`／`リリース済み`）を使います。**別の軸なので混ぜません。**

承認済みの版目標を変える場合は、AIが理由・影響・代案を示し、人が承認します。返答がない間は元の版に残します。

## 公開前の注意

このテンプレート自体に個人情報や認証情報は含めません。コピー先でも、`.env`、APIキー、OAuth JSON、トークン、パスワード、秘密鍵、支払い情報、実在利用者のデータ、権利不明の素材をGitへ入れないでください。

このテンプレートは[MIT License](./LICENSE)です。コピーして自由に使い、改変し、再配布できます。**コピー先のライセンスは、あなたが作るものに合わせて選び直してください。**このテンプレートのライセンスが、あなたの成果物へ自動的に及ぶわけではありません。

Node.jsを利用できる場合、編集中と共有前には次を実行します。未追跡の新規ファイルも検査対象です。

```powershell
node tools/check-template.mjs
```

commitまたはreleaseの前は、含めるファイルをGitへステージした後、必須ファイルがすべて追跡対象になっていることも確認します。

```powershell
node tools/check-template.mjs --require-tracked
```

検査するもの: 文書間のリンク切れ、必須文書の有無、AI別入口がAGENTS.mdの薄い参照だけか、秘密値らしい文字列（GitHub・Googleのトークン、`sk-`で始まる鍵、秘密鍵のPEM）、個人PCの絶対パス、Gitへ入れてはいけないファイル名、LICENSEの有無、未記入欄の残存（警告）。`--require-tracked`では、必須文書を作っただけでGitへ含め忘れていないかも検査します。

**これは最後の網であって、[docs/SECURITY.md](./docs/SECURITY.md)の代わりにはなりません。**検査を通っても、実データや権利の分からない素材は自分で確認してください。

### GitHub上で検査を走らせるか決める

同じ検査を[.github/workflows/check.yml](./.github/workflows/check.yml)でGitHub上でも実行できます。**手元にNode.jsが無くても使えます。**

**初期状態では手動起動です。**Actionsタブで自分が押したときだけ動きます。**勝手に動いて利用枠を消費しないようにしてあります。**

**先に費用を確認してください。**GitHub Actionsには実行時間の枠があります。

- **公開リポジトリ**: 標準のランナーなら無料
- **非公開リポジトリ**: 毎月の無料枠があり、超えた分は課金される

枠の大きさは契約プランで違います。現在の残量と上限は GitHub の Settings → Billing で確認してください。この検査自体は1回1分未満ですが、**自分のテストを足すと伸びます。**

そのうえで、次から選びます。

| 選択 | 設定 | 向いている場合 |
|---|---|---|
| **自動で走らせる** | `check.yml`の`pull_request:`か`push:`のコメントを外す | 公開リポジトリ。忘れても確実に検査したい |
| **走らせるか都度決める** | 初期状態のまま（手動起動） | 非公開リポジトリ。枠を気にしたい |
| **使わない** | `.github/workflows/check.yml`を削除する | 手元で`node tools/check-template.mjs`を実行できる |

**「使わない」を選んでも、手元での検査は必ず行ってください。**GitHub上で走らせるかどうかの話であって、検査そのものを省く選択ではありません。

決めた内容は[docs/RESOURCES.md](./docs/RESOURCES.md)の開発ツールの表へ記録します。自分のプロジェクトのテストを足す場所は`check.yml`の中に用意してあります。
