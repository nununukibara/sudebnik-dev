# AI COMPATIBILITY

複数のAI・IDE・CLIへ同じ開発規則を渡し、片方だけ古くなる事故を防ぐための方針です。

## 正本はAGENTS.mdだけ

[AGENTS.md](../AGENTS.md)を、AIが従う共通規則の唯一の正本とします。

AIごとに自動で読むファイル名や読込方式が異なるため、入口ファイルが必要な場合はあります。ただし、**AGENTS.mdの本文をコピーしません。**入口はimportまたは参照だけの薄いアダプターにします。

本文を複製しない理由:

- 片方だけ修正され、古い規則と新しい規則が同時に存在する
- 複数の命令ファイルを読むAIで、重複や矛盾が増える
- 毎回読み込む文量が増え、重要な規則が埋もれる
- どれが正本かを次のAIが判断できなくなる

過去の規則はGit履歴で確認します。入口ファイルへ版番号や進捗を書き写しません。

## 同梱する入口

| AI・利用経路 | 自動読込の入口 | このテンプレートでの扱い | 読込確認 |
|---|---|---|---|
| Codex | `AGENTS.md` | 直接読む | 新しいセッションで、現在の作業規則を要約させる |
| Cursor Agent / CLI | ルートの`AGENTS.md` | 直接読む | 新しいセッションで、変更前の必須手順を答えさせる |
| Claude Code | `CLAUDE.md` | `@AGENTS.md`でimportする | `/memory`で読込ファイルを確認する |
| Gemini CLI | `GEMINI.md` | `@./AGENTS.md`でimportする | `/memory show`。更新後は`/memory reload`する |
| GitHub Copilot | 利用画面により`AGENTS.md`または`.github/copilot-instructions.md` | 後者はAGENTSを正本として参照する互換入口。独自規則は持たせない | Copilot CLIは`/instructions`、他の画面は新しいセッションで要約させる |
| その他・ブラウザだけのAI | 製品ごとに異なる | リポジトリを読めなければREADMEの貼り付け手順を使う | AGENTSの「目標を守る」「標準ループ」「Gitと公開」を説明できるか確かめる |

公式仕様は更新されます。ファイルが置いてあるだけで利用可能と見なさず、実際に使うAIの接続・権限と一緒に[RESOURCES.md](./RESOURCES.md)へ読込確認を記録します。命令ファイルを更新した後は、継続中の会話へ自動反映されると仮定せず、新しいセッションまたは各製品の再読込機能で確認します。

### Copilotで複数の入口が見える場合

GitHub Copilotは利用画面によって対応する命令ファイルが異なります。GitHub.comのCopilot Chatでは`.github/copilot-instructions.md`が入口になり、coding agent・code review・Copilot CLIなどでは`AGENTS.md`も対象になります。そのため、このテンプレートはCopilot用の互換入口を残します。

`.github/copilot-instructions.md`には独立した作業規則を書かず、「ルートのAGENTS.mdを開いて読む」という通常の参照指示だけを置きます。Copilot CLI固有の`@` importには依存しません。Copilot CLIは適用対象の命令ファイルを組み合わせ、同一内容の重複を除きますが、一般的な優先順位は保証していません。両方が見えること自体は正常ですが、内容が競合する状態は作りません。

GitHub.comを含む各画面が、参照指示に従ってAGENTS.md本文を取得できるとは事前に仮定せず、[AI入口の受け入れ確認](#ai入口の受け入れ確認)を実行します。AGENTS.mdの規則を説明できなければ、RESOURCESへ`制限あり`と記録し、READMEの貼り付け手順を使います。規則本文を互換入口へコピーして埋め合わせません。

## 入口を古くしない検査

`node tools/check-template.mjs`は、入口ファイルが存在し、決めたimportだけを持つことを確認します。AI固有の規則を入口へ追加したくなった場合も、まず共通化できないか検討します。

本当にAI固有である場合は、次を満たしてから追加します。

1. 共通規則と矛盾しない
2. そのAIでしか意味を持たない理由がある
3. 読込確認方法がある
4. `tools/check-template.mjs`の期待値と、この文書を同時に更新する

## 能力差を前提にする

共通規則では、特定製品のツール名を必須にしません。作業開始時に次を実測し、無い能力には代替手段を決めます。

| 能力 | 望ましい使い方 | 無い場合の代替 |
|---|---|---|
| ファイルの読み書き | 正本を読み、差分を小さく反映する | 人が指定順に文書を貼り、AIの出力を転記する |
| コマンド実行 | テスト、lint、buildを実測する | 人が提示されたコマンドを実行し、秘密を除いた結果を返す |
| Git操作 | ブランチ、差分、履歴を確認する | 人が操作し、AIは実行前後の確認表を出す |
| サブエージェント | 独立した調査やレビューを分担する | 主担当が順番に行い、自己レビューとテストを分ける |
| Web・外部連携 | 公式仕様や外部状態を確認する | 未確認と明記し、人へ確認手順を渡す |
| 画像・音・実端末 | 主観品質や環境差を確認する | 判断者へ操作、期待結果、共有してほしい情報を示す |

能力が無いことを理由に最終目標を縮小しません。順序、担当、検証方法を変える提案として判断者へ示します。

## Superpowersから学ぶ範囲

[Superpowers](https://github.com/obra/superpowers)は、共通のskill本文と、AI環境ごとの薄いアダプター・起動処理・ツール対応表を分けています。このテンプレートでは、安定版[v6.2.0](https://github.com/obra/superpowers/releases/tag/v6.2.0)（MIT License）を設計参考として固定し、`main`の変更を無断で取り込みません。

人気や知名度だけで全部を採用せず、**何を防ぐための仕組みか**を先に見ます。不採用は否定ではなく、現在のテンプレートに必要な重さかどうかの判断です。

| 要素 | 元の意図 | このテンプレートでの扱い | 再検討する条件 |
|---|---|---|---|
| 共通skillとAI別アダプター | 共通手順を保ち、環境ごとの読込・ツール差だけを吸収する | **採用。**AGENTSを正本にし、入口だけ分ける | 新しいAIを正式対応へ加えるとき |
| 自動bootstrap・session hook | 利用者がskillを呼び忘れても、必要な手順を最初から効かせる | **調整。**repo内の自動読込ファイルを使い、外部プラグイン導入は必須にしない | 入口だけでは読込が安定しないと実測されたとき |
| TDDのRED→GREEN→REFACTOR | 実装後に都合のよいテストを書くのを防ぎ、要求した振る舞いを固定する | **採用。**詳細は[TESTING.md](./TESTING.md#テスト駆動開発tdd) | 自動化できない種類は、例外と代替確認を明記する |
| 系統的なデバッグ | 推測修正を重ねず、症状の再現と原因の証拠から直す | **採用。**不具合は再現テストから始める | 再現不能なら追加情報を求め、未確認とする |
| 完了前の独立した検証 | 「直したはず」を完成報告にしない | **採用。**新しいコマンド結果と差分確認を必要とする | 常に適用する |
| 全作業前の設計・承認ゲート | 要求を取り違えたまま実装を始めるのを防ぐ | **調整。**PROJECT_BRIEF、REQUIREMENTS、止まる条件を変更規模に応じて使う | 仕様が曖昧、外部影響、互換性変更があるときは必須 |
| 仕事ごとのサブエージェントと二段階レビュー | 主担当の文脈を守り、仕様適合とコード品質を別に確認する | **任意。**利用可能性、使用量、秘密情報、競合範囲を確認してから使う | 独立した作業が複数あり、分担利益が費用を上回るとき |
| 作業ごとのGit worktree | 並行変更の混線と上書きを避ける | **任意。**初心者の単独作業には必須化しない | 複数AIが同時に別範囲を変更するとき |
| skill・pluginとしての配布 | 複数repoへ同じ自動手順を導入しやすくする | **保留。**このテンプレートは製品非依存で、追加インストール無しを優先する | 複数repoで同じ手順を自動更新する必要が出たとき |
| 全AI環境の大規模な行動テスト | 説明文が実際にAIの行動を変えるか確認する | **軽量化。**新しいセッションで規則を説明させる受け入れ確認を行う | AI連携自体を製品機能として配布するとき |
| CIの常時自動実行 | 人が検査を忘れても品質ゲートを通す | **判断者選択。**既定は手動で、費用・利用枠を確認して自動化する | 公開repo、または利用枠と費用が確定したとき |
| テスト前に存在したコードの一律破棄 | 実装へテストを合わせる後付けTDDを防ぐ | **調整。**新規実装はREDへ戻すが、既存・利用者コードは保存し特性テストから始める | 破棄可能な未採用試作だけを扱うとき |

外部設計を今後追加するときも、参照先、確認したtagまたはcommit、ライセンス、採用部分、調整・保留部分、再検討条件をこの形式で残します。

## AI入口の受け入れ確認

新しいAIを使い始めるとき、または入口を変更したときは、製品ごとに新しいセッションを作り、コードを変更させる前に次を質問します。

```text
このリポジトリで読み込んだ命令ファイルを挙げ、
作業開始前に行うこと、AIが独断で変えてはいけないこと、
変更を完了と報告する前の確認を要約してください。
まだファイルは変更しないでください。
```

AGENTS.mdの現在の規則と一致しない場合、そのAIを`利用可能`にせず、[RESOURCES.md](./RESOURCES.md)へ`未確認`または`制限あり`として記録します。
