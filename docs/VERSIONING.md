# VERSIONING

最終目標を守りながら、開発を安全な大きさへ分ける規則です。

## 3つの目標を分ける

1. **最終目標** — 最終的に実現したい状態。PROJECT_BRIEFが正本
2. **正式版の目標** — その版で利用者へ約束する範囲。REQUIREMENTSが正本
3. **今回の作業目標** — 次の検証可能な小さな変更。STATUSが正本

今回の作業が小さくても、最終目標が小さくなったことにはなりません。

## SemVer

正式版は原則として`MAJOR.MINOR.PATCH`を使います。

- `MAJOR`: 互換性を壊す変更
- `MINOR`: 互換性を保つ機能追加
- `PATCH`: 互換性を保つ不具合修正

例: `1.4.2`

## 開発途中の版

- `1.1.0-alpha.1`: 大きな変更の開発中。未完成や既知の問題があり得る
- `1.1.0-beta.1`: 予定機能は概ね入り、実利用に近い確認を行う
- `1.1.0-rc.1`: 正式版候補。原則として重大な修正以外を増やさない
- `1.1.0`: 判断者が採用した正式版

全部を必ず使う必要はありません。ただし、未確認の版を正式版として扱いません。

## AIが版分割を提案するとき

次を1つの表で示します。

| 項目 | 内容 |
|---|---|
| 元の最終目標 | 何を守るか |
| 今回の版 | 何を完成・検証するか |
| 後の版 | 何が残るか |
| 分ける理由 | リスク、依存、学習、期限など |
| 各版の合格条件 | 誰が何を確認するか |

「難しいので削除」ではなく、「この順序なら目標を維持したまま確認できる」と説明します。

## 承認済みの版目標を固定する

判断者が版の目的と対象要件を承認した時点を、**版目標の基準**とします。

基準に含まれるもの:

- REQUIREMENTSでその版に割り当てられた要件
- 各要件の受け入れ条件
- PROJECT_BRIEFで約束した対象環境・品質・変えてはいけない条件
- ROADMAPにある版の目的と確認方法

承認後、AIは次を独断で行いません。

- 対象要件を後の版へ移す
- 要件や受け入れ条件を削除・緩和する
- 対応環境を減らす
- 「必須ではない」と再分類する
- 未実装の項目を一覧から消して版を完成扱いする

技術的な理由で変更が必要な場合、AIは次を提示します。

| 項目 | 内容 |
|---|---|
| 対象 | 版と要件ID |
| 理由と証拠 | 再現結果、依存、制約など |
| この版へ残す場合 | 費用、期間、リスク |
| 後へ移す場合 | 利用者と他要件への影響 |
| 代案 | 目標を維持できる別の順序・方法 |
| 提案する移動先 | 後の版または再検討時期 |

判断者が承認するまでは元の版へ残します。返答がない、AIの使用量が切れた、実装が難しい、期限が近いという理由だけで後へ移しません。進められない場合はSTATUSの判断待ちまたは中断として報告します。

承認後にREQUIREMENTSとROADMAPを書き直し、承認者・理由・変更前後をWORKLOGへ残します。

## 検討事項・追加事項を確認する節目

次の時点で、AIはPROJECT_BRIEF、REQUIREMENTS、ROADMAP、実装を照合し、判断者へ確認します。

1. 新しい版の計画を作る前
2. Alphaなどの大きな検証が終わった後
3. BetaまたはRCへ進む前
4. 正式版にする前

確認すること:

- 利用者の目標や優先度に変化がないか
- 追加したい利用場面・機能・品質条件がないか
- 新たに分かった制約、費用、安全性、互換性の問題がないか
- 後の版へ送る提案に未承認のものがないか
- 実装したが要件にないもの、要件にあるが未実装のものがないか

新しい案は自動的に現在の版へ追加しません。判断者が、現在の版、後の版、不採用、要調査のどれかを決めます。

## 版目標との照合

Beta、RC、正式版へ進む前に、対象版の各要件を次のいずれかへ分類して報告します。

- 実装・検証済み
- 実装済み・検証待ち
- 未実装
- 判断者の承認を得て後の版へ移動済み
- 判断待ちで版を止めている

未実装や判断待ちを隠して版を進めません。

## v1.0.0の考え方

v1.0.0は最初に実用できる正式版です。

- 主要な利用の流れを最初から最後まで完了できる
- 必須要件の受け入れ条件を満たす
- データ消失や秘密漏えいにつながる既知の重大問題がない
- 対応環境が明示されている
- 判断者が実物を確認している

機能の一部しか動かない試作は、v1.0.0ではありません。

## 版を確定する条件

1. 承認済みの版目標と現在の要件を照合し、無断の削除・後送りがない
2. 予定した要件が実装済み
3. [TESTING.md](./TESTING.md)の必要な確認が完了
4. 未確認項目と既知問題が文書化されている
5. STATUS、ROADMAP、仕様文書が実物と一致
6. 追加事項・再検討事項を判断者へ確認した
7. 判断者が採用を明示
8. その後にtagやreleaseを作る

AIだけで版を確定しません。

## 版番号の正本

実装開始後は、版番号を持つファイルを1つ決めてここへ記載します。

- 正本ファイル: 【未設定】
- 他の表示箇所: 【正本から生成／参照する方法】

同じ版番号を複数文書へ手作業で写しません。
