# VERSIONING

最終目標を守りながら、開発を安全な大きさへ分ける規則です。

## 3つの目標を分ける

1. **最終目標** — 最終的に実現したい状態。PROJECT_BRIEFが正本
2. **正式版の目標** — その版で利用者へ約束する範囲。REQUIREMENTSが正本
3. **今回の作業目標** — 次の検証可能な小さな変更。STATUSが正本

今回の作業が小さくても、最終目標が小さくなったことにはなりません。

## SemVer

正式版は原則として`MAJOR.MINOR.PATCH`を使います。

- `MAJOR`: 互換性を壊す変更
- `MINOR`: 互換性を保つ機能追加
- `PATCH`: 互換性を保つ不具合修正

例: `1.4.2`

### どれに当たるか迷ったときの参考

定義は上のとおりですが、実際の変更を当てはめる段で迷います。次は判断を助ける材料です。**規則ではありません。**

**利用者へのお知らせを書くつもりで考えます。**

> 「〜できるようになりました」と書けるなら`MINOR`。
> 「〜が直りました」しか書けないなら`PATCH`。

**手間が減っただけの変更は`PATCH`です。**手作業だった手順を自動にすると、コードは増えますが、利用者から見ると新しくできることは増えていません。

> 利用者が**新しく何かをする**ようになるなら`MINOR`。
> 前からできたことを**失敗しなくなっただけ**なら`PATCH`。

そのための操作が画面に増えても、それが元の作業へ戻るための操作なら`PATCH`のままです。

**作業の大変さでは決めません。**時間がかかった、コードを大きく書き換えた、というのは版の幅の根拠になりません。判定は必ず利用者から見て何が変わったかで行います。

これらは判断の材料であって、機械的に当てはめるものではありません。材料どうしが食い違う場合（例: 内部的には新しい処理だが、利用者には失敗が消えただけ）は、判断者へ確認します。**版を決めるのは判断者です。**

## 開発途中の版

- `1.1.0-alpha.1`: 大きな変更の開発中。未完成や既知の問題があり得る
- `1.1.0-beta.1`: 予定機能は概ね入り、実利用に近い確認を行う
- `1.1.0-rc.1`: 正式版候補。原則として重大な修正以外を増やさない
- `1.1.0`: 判断者が採用した正式版

全部を必ず使う必要はありません。ただし、未確認の版を正式版として扱いません。

## AIが版分割を提案するとき

次を1つの表で示します。

| 項目 | 内容 |
|---|---|
| 元の最終目標 | 何を守るか |
| 今回の版 | 何を完成・検証するか |
| 後の版 | 何が残るか |
| 分ける理由 | リスク、依存、学習、期限など |
| 各版の合格条件 | 誰が何を確認するか |

「難しいので削除」ではなく、「この順序なら目標を維持したまま確認できる」と説明します。

## 承認済みの版目標を固定する

判断者が版の目的と対象要件を承認した時点を、**版目標の基準**とします。

基準に含まれるもの:

- REQUIREMENTSでその版に割り当てられた要件
- 各要件の受け入れ条件
- PROJECT_BRIEFで約束した対象環境・品質・変えてはいけない条件
- ROADMAPにある版の目的と確認方法

承認後、AIは次を独断で行いません。

- 対象要件を後の版へ移す
- 要件や受け入れ条件を削除・緩和する
- 対応環境を減らす
- 「必須ではない」と再分類する
- 未実装の項目を一覧から消して版を完成扱いする

技術的な理由で変更が必要な場合、AIは次を提示します。

| 項目 | 内容 |
|---|---|
| 対象 | 版と要件ID |
| 理由と証拠 | 再現結果、依存、制約など |
| この版へ残す場合 | 費用、期間、リスク |
| 後へ移す場合 | 利用者と他要件への影響 |
| 代案 | 目標を維持できる別の順序・方法 |
| 提案する移動先 | 後の版または再検討時期 |

判断者が承認するまでは元の版へ残します。返答がない、AIの使用量が切れた、実装が難しい、期限が近いという理由だけで後へ移しません。進められない場合はSTATUSの判断待ちまたは中断として報告します。

承認後にREQUIREMENTSとROADMAPを書き直し、承認者・理由・変更前後をWORKLOGへ残します。

## 検討事項・追加事項を確認する節目

次の時点で、AIはPROJECT_BRIEF、REQUIREMENTS、ROADMAP、実装を照合し、判断者へ確認します。

1. 新しい版の計画を作る前
2. Alphaなどの大きな検証が終わった後
3. BetaまたはRCへ進む前
4. 正式版にする前

確認すること:

- 利用者の目標や優先度に変化がないか
- 追加したい利用場面・機能・品質条件がないか
- 新たに分かった制約、費用、安全性、互換性の問題がないか
- 後の版へ送る提案に未承認のものがないか
- 実装したが要件にないもの、要件にあるが未実装のものがないか

新しい案は自動的に現在の版へ追加しません。判断者が、現在の版、後の版、不採用、要調査のどれかを決めます。

## 版目標との照合

Beta、RC、正式版へ進む前に、対象版の各要件を次のいずれかへ分類して報告します。

- 実装・検証済み
- 実装済み・検証待ち
- 未実装
- 判断者の承認を得て後の版へ移動済み
- 判断待ちで版を止めている

未実装や判断待ちを隠して版を進めません。

## v1.0.0の考え方

v1.0.0は最初に実用できる正式版です。

- 主要な利用の流れを最初から最後まで完了できる
- 必須要件の受け入れ条件を満たす
- データ消失や秘密漏えいにつながる既知の重大問題がない
- 対応環境が明示されている
- 判断者が実物を確認している

機能の一部しか動かない試作は、v1.0.0ではありません。

## 保存したものを、次の版で開けるか

利用者のデータをファイルやデータベースへ保存する場合、**版を上げる前に必ず確認します。**

1. 今回、保存する形（項目、構造、意味）を変えたか
2. 変えたなら、**古い形で保存されたものをどう扱うか**

2の答えは次のどれかです。判断者が決めます。

- **そのまま読めるようにする**（古い形を読む処理を用意する）
- **変換する**（読み込み時に新しい形へ直す。変換前を残すかも決める）
- **読めなくてよい**（開発中でデータを捨てられる、利用者がいない、など）

**「読めなくてよい」も正当な結論です。**開発中に何度も形が変わるのは普通のことで、毎回互換を保つほうが有害な場合もあります。ただし、**決めずに進めない**でください。気づかないまま利用者のデータが開けなくなるのが最悪の結果です。

利用者がすでにいる状態でデータを読めなくする場合、それは`MAJOR`に当たります。

保存形式へ独立した版番号を持たせるかは、次の節で決めます。

## 別々に版を持つ部分があるか

実装を始める前に決めます。ほとんどのプロジェクトは版が1つで足ります。

- 別々に版を持つ部分: 【無し／あるなら、その一覧】
- ある場合、各々の版の付け方: 【SemVer／連番など】
- 製品全体の版との関係: 【どう決めるか】

**あとから分けるのは面倒です。**保存形式、外部へ公開するAPI、他の人が使うライブラリ部分は、製品本体と別の速さで変わることがあります。心当たりがあるなら最初に決めておきます。

一方、**無い場合は「無し」と書いて終わりです。**必要でないのに版を分けると、番号を合わせる作業だけが増えます。

## 既定ブランチと版

**既定ブランチ（`main`など）には、判断者が採用した版だけを置きます。**

開発中の版やAlpha、Beta、RCは作業ブランチに置き、正式版として採用すると決めた時点で版番号を正式版へ直してから既定ブランチへ入れます。

こうしないと、既定ブランチの版表記が`1.2.0-alpha.1`のようなまま残り、**どこへ戻れば安全か分からなくなります。**戻れる地点はタグで示します。

利用者の実データや、失うと取り返しがつかないデータを扱う場合は、**採用前の版をそれへ向けません。**複製したデータで確認します。

## 版を確定する条件

1. 承認済みの版目標と現在の要件を照合し、無断の削除・後送りがない
2. 予定した要件が実装済み
3. [TESTING.md](./TESTING.md)の必要な確認が完了
4. 保存する形を変えた場合、古いデータの扱いを判断者が決めている（[上記](#保存したものを次の版で開けるか)）
5. 未確認項目と既知問題が文書化されている
6. STATUS、ROADMAP、仕様文書が実物と一致
7. 追加事項・再検討事項を判断者へ確認した
8. 版番号が正式版になっている（プレリリース表記が残っていない）
9. 判断者が採用を明示
10. その後にtagやreleaseを作る

AIだけで版を確定しません。

## 版番号の正本

実装開始後は、版番号を持つファイルを1つ決めてここへ記載します。

- 正本ファイル: 【未設定】
- 他の表示箇所: 【正本から生成／参照する方法】

同じ版番号を複数文書へ手作業で写しません。写した時点で、いずれ片方が古くなります。

複数の版を持つ場合は「[別々に版を持つ部分があるか](#別々に版を持つ部分があるか)」で決めた分だけ、それぞれの正本を書きます。
