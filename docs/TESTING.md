# TESTING

「実装した」と「利用者が使える」を分けるための検証計画です。

## 確認の種類

| 種類 | 目的 | 主な担当 |
|---|---|---|
| 静的確認 | 構文、型、lint、危険な設定を見つける | AI・自動化 |
| 単体テスト | 小さな処理の入力と出力を固定する | AI・自動化 |
| 結合テスト | 複数部品や外部サービスの接続を確かめる | AI・自動化 |
| 回帰テスト | 修正で既存機能を壊していないか確かめる | AI・自動化 |
| 実環境テスト | 実端末、実ブラウザ、実ファイルで確かめる | AIまたは判断者 |
| 受け入れ確認 | 利用者の目的を最初から最後まで達成できるか確認する | 判断者 |

## GitHub上での自動実行

[.github/workflows/check.yml](../.github/workflows/check.yml)で、公開前検査と自分のテストをGitHub上で実行できます。

**既定は手動起動です。**自動で走らせるか、都度手動にするか、使わないかは判断者が決めます。**GitHub Actionsには実行時間の枠があり、非公開リポジトリでは超過分が課金される**ためです。選び方は[README.md](../README.md)、決めた内容は[RESOURCES.md](./RESOURCES.md)の`TOOL-04`へ記録します。

自分のプロジェクトのテストは、`check.yml`の「あなたのテスト」へ足します。

自動化する価値が高いのは、毎回同じ手順で、人が忘れやすいものです。逆に、見た目・音・操作感の確認は自動化できません。下の「判断者の操作が必要なもの」へ書きます。

## AIだけで確認できるもの

- 【自動テスト】
- 【APIや書き出し処理】
- 【異常系】

## 判断者の操作が必要なもの

- 【見た目、音、操作感、実端末、外部アカウントなど】

AIは判断者に依頼するとき、次を具体的に示します。

1. どこを開くか
2. 何を入力・操作するか
3. 正常なら何が見えるか
4. 問題があれば何を送るか
5. 秘密情報を画面共有・貼り付けしない注意

## 変更ごとの最低確認

- 変更箇所に直接関係するテスト
- 影響を受ける既存機能の回帰テスト
- 保存形式を変えた場合の旧データ読み込み
- UIを変えた場合の対象画面幅と操作
- 外部サービスを変えた場合の未設定、認証切れ、停止時の動作
- ファイル処理を変えた場合の破損、重複、名前衝突、容量不足

## 完了の条件（Definition of Done）

1つの要件を「完了」とするには、原則として次を満たします。

- 要件と受け入れ条件が承認済み
- 実装がある
- 必要な自動・手動テストを通した
- 既知の制約と未確認事項を報告した
- 文書が実物と一致する
- 判断者が採用した

## リリース前チェック（検証の側）

**確認の項目だけをここに置きます。**版を確定してよいかの条件は[VERSIONING.md](./VERSIONING.md)「版を確定する条件」、公開してよいかの条件は[SECURITY.md](./SECURITY.md)「公開前チェック」が正本です。3つを揃えて通します。

- [ ] 対象版の全要件に確認結果がある
- [ ] 自動テストが通る
- [ ] 主要な利用の流れを実環境で通した
- [ ] 旧データ・設定との互換性を確認した
- [ ] 依存関係が揃い、意図した版で動くことを確認した
- [ ] バックアップと復旧手順を確認した

依存関係とその素材の**ライセンス**は[SECURITY.md](./SECURITY.md)の「公開前チェック」で見ます。ここでは動くかどうかだけを見ます。

チェック結果と実行コマンドはWORKLOGへ記録します。
