# TESTING

「実装した」と「利用者が使える」を分けるための検証計画です。

## 確認の種類

| 種類 | 目的 | 主な担当 |
|---|---|---|
| 静的確認 | 構文、型、lint、危険な設定を見つける | AI・自動化 |
| 単体テスト | 小さな処理の入力と出力を固定する | AI・自動化 |
| 結合テスト | 複数部品や外部サービスの接続を確かめる | AI・自動化 |
| 回帰テスト | 修正で既存機能を壊していないか確かめる | AI・自動化 |
| 実環境テスト | 実端末、実ブラウザ、実ファイルで確かめる | AIまたは判断者 |
| 受け入れ確認 | 利用者の目的を最初から最後まで達成できるか確認する | 判断者 |

## テスト駆動開発（TDD）

### 何をTDDの対象にするか

**入力と期待結果を自動で確かめられる振る舞いの変更は、原則としてTDDで進めます。**新機能だけでなく、不具合修正、保存形式、API、変換、計算、画面状態、出力構造も対象です。

実装方法ではなく、利用者または呼び出し側から観察できる結果をテストします。受け入れ条件が曖昧なら、先に[REQUIREMENTS.md](./REQUIREMENTS.md)を整え、判断者へ確認します。

### RED → GREEN → REFACTOR

1. **RED** — 変更後に満たす振る舞いを、実装より先に1つのテストで表す
2. そのテストだけを実行し、**期待した理由で失敗した**ことを確認する。構文エラー、テスト設定の誤り、無関係な失敗はREDではない
3. **GREEN** — そのテストを通すための最小の変更を行う
4. 変更箇所のテストを通し、続けて影響範囲と全体の回帰テストを通す
5. **REFACTOR** — 重複や分かりにくさを整理する。整理中もテストが通る状態を保つ

1つのテストへ多くの振る舞いを詰めず、小さな単位でこの循環を繰り返します。

### 不具合修正

不具合修正は、報告された症状を再現する回帰テストから始めます。

1. 修正前のコードで症状が再現し、テストが失敗する
2. 失敗理由が報告された問題と一致する
3. 修正後にそのテストが通る
4. 関係する既存テストも通る

再現できない場合は、推測で修正せず、再現条件、ログ、入力、環境の不足を報告します。

### 既存コードと未テストの処理

既存コードや利用者の作業を、テストより先に書かれたという理由だけで削除しません。まず現在の振る舞いを固定する**特性テスト**を追加し、その後に変更したい振る舞いの失敗テストを作ります。

新しく書いた未確定の実装が先行してしまった場合は、その実装を正解としてテストを合わせません。受け入れ条件へ戻り、実装が無い状態でも失敗するテストを確認してから続けます。

### TDDの例外

次は自動テストを先に書けない場合があります。

- 文言だけの文書修正
- 自動生成され、生成元を別に検証しているコード
- 捨てる前提の技術調査。製品へ入れる場合はTDDで作り直す
- 見た目の好み、音の自然さ、操作感など、人の判断が結果そのものになる確認
- 実端末や外部サービスが必要で、安定した自動化が現時点では不可能な確認

例外はAIが黙って決めません。理由、影響、代わりに行う静的確認・手動確認・受け入れ確認をWORKLOGへ記録し、必要なら判断者へ確認します。自動化できる部分まで例外に含めません。

### UI・動画・音の分け方

主観的な品質がある機能も、全部が手動確認になるわけではありません。

| 自動化しやすいもの | 人が確認するもの |
|---|---|
| 要素の有無、状態遷移、寸法、比率、レイヤー順、フレーム数、音量値、出力形式、メタデータ | 見やすさ、雰囲気、音の自然さ、聞き取りやすさ、操作の分かりやすさ |

自動テストで構造を固定し、人の確認で品質を判断します。片方をもう片方の代わりにしません。

### 記録する証拠

WORKLOGとPull Requestには、該当する範囲で次を残します。

- REDで実行したテストと、期待した失敗
- GREENで通した対象テスト
- 影響範囲または全体の回帰テスト
- TDDの例外と代替確認
- 人だけが確認する残り

「テスト済み」だけではなく、実行したコマンドと結果を書きます。別AIや補助担当の報告だけで完了扱いにせず、主担当が差分と新しい検証結果を確認します。

## GitHub上での自動実行

[.github/workflows/check.yml](../.github/workflows/check.yml)で、公開前検査と自分のテストをGitHub上で実行できます。

**既定は手動起動です。**自動で走らせるか、都度手動にするか、使わないかは判断者が決めます。選び方と費用・利用枠の確認方法は[README.md](../README.md#github上で検査を走らせるか決める)、決めた内容は[RESOURCES.md](./RESOURCES.md)の`TOOL-04`へ記録します。

自分のプロジェクトのテストは、`check.yml`の「あなたのテスト」へ足します。

自動化する価値が高いのは、毎回同じ手順で、人が忘れやすいものです。逆に、見た目・音・操作感の確認は自動化できません。下の「判断者の操作が必要なもの」へ書きます。

## AIだけで確認できるもの

- 【自動テスト】
- 【APIや書き出し処理】
- 【異常系】

## 判断者の操作が必要なもの

- 【見た目、音、操作感、実端末、外部アカウントなど】

AIは判断者に依頼するとき、次を具体的に示します。

1. どこを開くか
2. 何を入力・操作するか
3. 正常なら何が見えるか
4. 問題があれば何を送るか
5. 秘密情報を画面共有・貼り付けしない注意

## 変更ごとの最低確認

- TDD対象なら、期待したREDとGREENの記録
- 変更箇所に直接関係するテスト
- 影響を受ける既存機能の回帰テスト
- 保存形式を変えた場合の旧データ読み込み
- UIを変えた場合の対象画面幅と操作
- 外部サービスを変えた場合の未設定、認証切れ、停止時の動作
- ファイル処理を変えた場合の破損、重複、名前衝突、容量不足

## 完了の条件（Definition of Done）

1つの要件を「完了」とするには、原則として次を満たします。

- 要件と受け入れ条件が承認済み
- 実装がある
- TDD対象では、REDから始めた証拠がある。例外なら理由と代替確認がある
- 必要な自動・手動テストを通した
- 既知の制約と未確認事項を報告した
- 文書が実物と一致する
- 判断者が採用した

## リリース前チェック（検証の側）

**確認の項目だけをここに置きます。**版を確定してよいかの条件は[VERSIONING.md](./VERSIONING.md)「版を確定する条件」、公開してよいかの条件は[SECURITY.md](./SECURITY.md)「公開前チェック」が正本です。3つを揃えて通します。

- [ ] 対象版の全要件に確認結果がある
- [ ] 自動テストが通る
- [ ] 主要な利用の流れを実環境で通した
- [ ] 旧データ・設定との互換性を確認した
- [ ] 依存関係が揃い、意図した版で動くことを確認した
- [ ] バックアップと復旧手順を確認した

依存関係とその素材の**ライセンス**は[SECURITY.md](./SECURITY.md)の「公開前チェック」で見ます。ここでは動くかどうかだけを見ます。

チェック結果と実行コマンドはWORKLOGへ記録します。
