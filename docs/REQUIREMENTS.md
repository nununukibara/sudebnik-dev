# REQUIREMENTS

合意済みの機能要件・品質要件と、その受け入れ条件の正本です。

候補段階の要望はここへ確定記載せず、[STATUS.md](../STATUS.md)の「判断待ち」またはGitHub Issueへ置きます。

## 書き方

- `F-001`: 利用者から見える機能
- `Q-001`: 性能、信頼性、使いやすさ、安全性などの品質
- `C-001`: 法律、予算、環境、互換性などの制約
- IDは一度割り当てたら使い回さない
- 「できること」だけでなく、観察可能な受け入れ条件を書く
- 対象版はこの表を正本とし、ROADMAPはIDを参照する

## 対象版が承認された後

ROADMAPで版の状態が`承認済み`になった時点で、その版の要件、受け入れ条件、対象版は版目標の基準になります。

AIは判断者の承認なく、対象版を書き換えたり、受け入れ条件を弱めたり、行を削除したりしません。実装できていない要件も残し、STATUSで未実装・判断待ちとして扱います。

## 要件から外すとき

要件の削除や後送りは、判断者の承認が必要です。

1. AIが対象版と要件ID、理由と証拠、影響、代案、後送り先の版を示す
2. 判断者が採否を決める
3. 決定理由をWORKLOGへ残す
4. この文書とROADMAPを現在の合意へ書き直す

判断者から返答がない場合は変更しません。元の対象版に残し、STATUSの判断待ちへ置きます。

過去の要件はGit履歴で参照します。廃止一覧を本文へ積み上げません。

## 新しい要件を見つけたとき

AIは、実装中に見つけた追加案を黙って現在の版へ混ぜません。

1. 既存要件を満たすために必要な不足、独立した新機能、安全性・互換性上の必須対応のどれかへ分類する
2. 目的、受け入れ条件、対象版の案、期間・互換性への影響を示す
3. STATUSの判断待ちまたはGitHub Issueへ置く
4. 判断者が採用と対象版を決めた後、この文書へ追加する

安全性やデータ損失に関わる場合はリリースを止める提案ができますが、判断結果を待たずに要件を削ることはできません。
